# Diagram

문서의 이해를 돕는 도식만 만든다. **그림을 넣는 것보다 넣을 필요가 있는지 판단하는 것이 먼저다.**
사용자가 지정한 diagram 스킬의 판정·검토 절차를 이 저장소의 Jekyll 출판 환경에 맞게 옮겼다.
원본 프로젝트의 업무 예시·구현 경로·테마 토큰·대비 실측값은 가져오지 않는다.

먼저 `AGENTS.md`, `docs/writing-convention.md`와 대상 본문을 읽는다.
Wiki라면 `.agents/skills/wiki/SKILL.md`와 `docs/wiki-authoring.md`도 읽는다.
문체·학습 기준은 해당 정본을 따르며 이 스킬에 복제하지 않는다.
모델·CLI에 종속되지 않는다. 자동 탐색·`/diagram` 메뉴 지원은 도구마다 다르며,
지원하지 않으면 이 파일을 직접 읽어 수행한다. 질문·평가는 조회·제안으로 끝내고,
작성 요청일 때만 승인한 범위의 문서와 도식을 수정한다.

## 1. 그릴지 판단한다

기준은 **잘 쓴 한 문단보다 독자가 더 얻는가**다. 다음 관계가 이해의 병목일 때 그린다.

| 전달할 관계 | 적합한 형태 |
|---|---|
| 데이터 경로와 실행·저장·트랜잭션 경계 | 흐름도와 경계 상자 |
| 조건에 따른 갈림과 결과 | 분기 흐름도 |
| 공간·소유권·동시에 존재하는 구성 요소 | 레인·묶음 |
| 앞뒤 시점과 겹쳐 일어나는 작업 | 시간축·타임라인 |

- 설정 키·기본값·금지 목록·필드 나열은 표나 목록으로 둔다. 관계가 없으면 선을 만들지 않는다.
- 순서·경로를 담은 표나 ASCII 그림은 교체할 수 있다. 같은 관계를 원본과 새 그림에 중복해서 두지 않는다.
- 기존 도식이 같은 관계를 충분히 설명하면 새로 그리지 않는다.
- 노드가 여러 개 이어진 한 줄도 관계를 표현하는 그림이다. 단순하다는 이유만으로 기각하지 않는다.
- 복잡하면 개념적으로 나뉘는 경계에서 쪼갠다. 노드 예산을 넘었다는 이유로 필요한 그림 자체를 포기하지 않는다.
- 짧은 절에 그림이 셋을 넘으면 각각의 목적을 다시 점검한다. 장을 합친 긴 교과서에 그림 셋이라는 전체 상한을 적용하지 않는다.

## 2. 그림이 말할 한 가지를 정한다

그 절의 어려운 한 문장을 그림의 결론으로 삼는다. 실행 배치와 데이터 이동, 복제와 업무 완료,
원자성과 단순 전달을 구분한다. **화살표만으로 동시 완료·무손실·exactly-once를 암시하지 않는다.**

1. 실제 구성 요소·상태·주체를 본문과 근거에서 추출한다. 그림 때문에 단계를 새로 지어내지 않는다.
2. 각 선의 의미(레코드 이동·요청·할당·재개 위치 등)를 정한다. 다른 의미의 선은 라벨 또는 형태로 구분한다.
3. 본문에서 쓰는 이름과 예시 값을 유지한다. 정상 경로부터 그리고 필요할 때 실패 조건을 추가한다.
4. 한 그림의 단계 노드는 대략 9개 이내, 강조점은 1~2개로 제한한다. 공간 경계는 단계 노드와 구분한다.
5. 분기마다 조건을 붙인다. 여러 작업이 동시에 진행된다면 하나의 직렬 흐름처럼 그리지 않는다.

## 3. 현재 렌더러에 맞춰 작성한다

이 저장소는 Jekyll Markdown에서 `![설명](/assets/images/...)`로 정적 SVG를 표시한다.
Kafka의 기존 자산은 `assets/images/kafka-textbook/`에 있다. 다른 주제는 대상의 기존 자산 규칙을 먼저 확인한다.
Post 이미지에는 별도의 첨부 출판 규칙이 있으므로 Wiki의 파일 저장 규칙을 그대로 적용하지 않는다.
Next.js JSX·Tailwind 유틸·Mermaid 런타임을 옮기거나 새 클라이언트 라이브러리를 설치하지 않는다.

- SVG를 정본으로 삼거나, 반복 생성이 필요하면 `scripts/`의 생성기를 정본으로 삼는다. 생성기와 결과를 함께 검증하며 새로운 그림을 만들다가 기존 자산 전체를 재생성하지 않는다.
- 독립 SVG는 부모 페이지의 CSS 변수나 글꼴을 자동 상속하지 않는다. 이 저장소의 기존 도식처럼 **불투명한 밝은 도판**을 쓰는 경우 색을 SVG 내부에 명시하고 라이트·다크 페이지 양쪽에서 확인한다. 테마를 상속한다고 보고하지 않는다.
- 새 그림은 기존 도식의 팔레트·선·글꼴과 맞춘다. 채움·선 굵기·공간 경계로 강조하고 색만으로 정보를 구별하지 않는다. 그림자·그라디언트·장식 아이콘을 넣지 않는다.
- 시작·끝은 타원, 단계는 사각형, 조건 분기는 마름모를 기본으로 한다. 단순 관계도에 불필요한 시작·끝 노드를 추가하지 않는다.
- 연결선은 수평·수직과 둥근 직각 엘보를 우선한다. 선을 노드보다 먼저 그리고 라벨을 가로지르지 않게 한다.
- 좌표·크기·간격은 4px 격자를 우선한다. 글자를 줄여 억지로 끼워 넣지 않는다.
- 모바일 본문에서 결론이 읽히는 폭으로 만든다. 복잡하면 여러 그림으로 나누거나 위→아래로 전개한다. 큰 `viewBox`를 폭에 맞춰 축소해 글자를 못 읽게 만들지 않는다. 사이트 UI·CSS는 별도 승인 없이 바꾸지 않는다.
- SVG에 고유 접두사의 `<title>`·`<desc>`와 `role="img"`, `aria-labelledby`를 제공한다. Markdown 대체 텍스트도 그림의 관계를 설명한다.
- 그림에 스크립트·외부 이미지·외부 폰트 의존성을 넣지 않는다. 고정 수치와 기술적 식별자에만 모노스페이스를 쓴다.

## 4. 그림 가까이에서 본문을 연결한다

관계만 반복하던 ASCII 그림은 새 도식으로 교체한다. 그림이 말한 순서를 문단·표·캡션에 그대로 다시 적지 않는다.
다만 **정의·설계 이유·전제·실패 조건·보장 범위**는 그림으로 옮겼다는 이유로 지우지 않는다.
학습용 설명의 자기완결성을 분량 감소보다 우선한다. 산문 감소율을 품질 목표로 삼지 않는다.
캡션에는 그림이 못 말하는 조건이나 표기 범위를 짧게 남긴다. 기본 설명을 토글에 숨기지 않는다.

## 5. 빌드하고 실제 그림을 확인한다

1. SVG XML 파싱, 참조 파일 존재, 고유 접근성 ID, 문서 링크와 출판 제외 경계를 검사한다.
2. SVG에 실제 도형·연결선이 있는지 확인한다. 외부 SVG는 페이지 HTML에 `<path>`가 없는 것이 정상일 수 있으므로 이미지 파일 자체를 검사한다. `<path>` 개수만으로 기술적 의미를 검증하지 않는다.
3. 일반 Jekyll 빌드 뒤 **실제 렌더된 문서**를 열어 데스크톱·모바일, 라이트·다크에서 본다. 스크린샷으로 겹침·잘림·너무 작은 글자·화살표 방향을 확인한다.
4. 텍스트는 4.5:1, 의미 있는 윤곽·화살표는 3:1 이상인지 계산한다. 배경이 아니라 실제 도형 채움과 비교하고 투명색은 합성 후 계산한다. 장식용 채움이나 배경색 후광은 별도로 구분한다.
5. 본문·근거와 각 경계·화살표·상태를 대조한다. 린트·XML 파싱·스크린샷만으로 기술 정확성을 입증했다고 하지 않는다.
6. 요청한 파일만 검증·커밋·푸시한다. 배포를 보고할 때는 일치하는 Pages 실행과 공개 이미지·본문을 확인한다. `.agents`와 작성·검증 자료는 사이트에서 제외되어야 한다.

실제로 확인한 것과 못 확인한 것을 구분해 보고한다. 공개 저장소에는 비공개 업무 사례·개인 경로·인증정보·미리보기 스크린샷을 넣지 않는다.
