# 학습용 Wiki 작성·검증

이 저장소의 위키를 짧은 요약이 아닌 학습용 교과서로 작성·보강할 때 적용한다.
공통 작업 규칙은 `AGENTS.md`, 문체 기준은 `docs/writing-convention.md`가 정본이다.

## 호출

공용 스킬: `.agents/skills/wiki/SKILL.md`. 모델이나 CLI에 관계없이 이 파일을 읽어 사용한다.
요청 예시:

```text
/wiki Redis 학습용 교과서로 만들어줘
/wiki Kafka 중복과 누락을 설명하는 장을 보강해줘
/wiki Kafka 각주와 장 참조를 검토해줘
```

`AGENTS.md`가 공용 스킬을 안내한다. `$ARGUMENTS` 같은 특정 CLI 문법은 사용하지 않는다.
자동 스킬 탐색과 `/wiki` 메뉴 등록 여부는 도구마다 다르다. 모든 도구에서 자동 등록된다고 가정하지 않는다.
미지원 도구에는 “`.agents/skills/wiki/SKILL.md`를 읽고 Redis 위키를 작성해줘”처럼 요청한다.
Hermes 전역 스킬이나 특정 도구 설치에 의존하지 않는다.
대상 없는 호출은 대상만 묻는다. 질문·평가는 조회·제안으로 끝내고 파일을 바꾸지 않는다.
신규 문서의 범위·독자 수준이 불명확하면 목차와 한 절의 예시를 먼저 제안한다.
이미 승인된 범위는 다시 승인받지 않는다. Ouroboros는 명시적으로 요청할 때만 사용한다.

## 학습용 교과서의 깊이

Wiki 본문 자체가 교과서다. 요약 위키와 별도 원고로 이중 관리하지 않는다.
공식 문서의 메뉴 순서 대신 이해에 필요한 선행 개념 순서로 구성한다.
독자가 다음을 설명할 수 있도록 핵심 개념을 본문에서 충분히 다룬다.

- 어떤 문제가 있어서 이 기술이 필요한가.
- 구성 요소가 어디에 있고 누가 무엇을 담당하는가.
- 입력이 각 단계를 어떻게 통과하는가.
- 왜 이 구조를 택했으며 어떤 비용을 줄이고 무엇을 포기했는가.
- 무엇을 어떤 조건에서 보장하며 장애·재시도·설정 변경 시 무엇이 달라지는가.
- 앞서 배운 개념이 다음 설계 판단과 어떻게 연결되는가.

이를 매 절의 동일한 소제목 템플릿으로 강제하지 않는다.
핵심 원리는 부록이나 해설 토글에 숨기지 않는다. 참고용 세부 설정은 분리할 수 있다.
주차·공부 시간·강제 실습·기록 양식을 임의로 덧붙이지 않는다.
확인 질문은 선택적으로 제공하고 해설은 기존 본문 토글을 이용한다.
Kafka는 설명 깊이의 참고이며 장 수·목차를 다른 기술에 복제하지 않는다.

### 본문만으로 이해할 수 있는 범위

독자는 선언한 선수 지식만 가진 상태에서 처음부터 읽고, 다룬 핵심 개념의 의미와 동작을 자기 말로 설명할 수 있어야 한다. 모든 현장 문제를 책만으로 해결하게 만드는 목표와는 구분한다. 기본 개념을 이해하기 위해 외부 문서를 찾아야 한다면 본문의 설명 공백이다.

- 정의 한 문장이나 기능 목록은 설명 완료가 아니다. 실제 실행 위치, 입력·출력, 담당 주체, 정상 동작의 순서와 설계 이유를 연결한다.
- 제품·프레임워크·플러그인·설정·실행 인스턴스를 구분한다. “설치한다”, “등록한다”, “실행한다”의 대상이 무엇인지 설명한다.
- 용어가 다른 용어로만 정의되는 순환을 피한다. 선행 개념은 앞서 가르치거나 필요한 자리에서 짧게 설명한다. 뒤 장의 세부사항은 예고할 수 있지만 현재 흐름의 이해를 맡기지 않는다.
- 정상 동작을 이해시킨 뒤 예외·보장 한계·운영 설정을 붙인다. 주의사항이 상세하다는 이유로 기초 설명이 충분하다고 판단하지 않는다.
- 공식 문서는 주장 검증·심화·버전별 옵션 확인을 위한 근거다. 본문의 원리 설명을 대신하는 링크 목록으로 쓰지 않는다.
- 독자가 직접 경험하거나 찾아볼 범위는 제품별 전체 옵션, 환경별 설치, 성능 측정과 현장 장애 대응이다. 설명에 필요한 전제는 본문에 남긴다.

### 인지과학을 고려한 설명 설계

아래는 독자의 이해를 돕기 위한 편집 원칙이다. 특정 문서의 학습 효과를 실험으로 입증했다는 뜻은 아니다. 짧게 쓰기와 학습 부담 줄이기는 같지 않다. 연결 고리를 지워 독자가 머릿속에서 복원하게 만들면 문장 수만 줄어든다.

1. **선행 지식과 단계적 설명:** 먼저 개념의 역할을 익히고, 한 입력의 정상 흐름을 따라간 뒤, 같은 흐름에 복제·재시도·장애 등 복잡성을 추가한다. 본문 처음에 모든 설정·예외를 한꺼번에 제시하지 않는다.
2. **풀이된 사례:** 이름과 값을 가진 작은 사례의 입력 → 중간 상태 → 결과를 설명한다. API·설정 예시는 각 항목이 그 흐름의 무엇을 바꾸는지 해설한다. 실행 예제와 설명용 부분 예제를 명확히 구분한다.
3. **구체적 사례와 일반 원리 연결:** 사례 뒤에는 어떤 조건이 일반화되는지 밝힌다. 입력·환경·실패 시점을 하나 바꾼 반례로 적용 범위를 확인한다. 비유가 실제 구조를 대신하지 않게 한다.
4. **그림과 설명 연결:** 그림이 실행 배치·데이터 이동·시간 순서 중 무엇을 나타내는지 밝힌다. 필요한 설명을 그림 가까이에 두고 동일한 이름을 사용한다. 그림을 여러 서버로 오해하거나 화살표를 원자성 보장으로 오해할 여지를 해소한다.
5. **회상과 자기 설명:** 선택적 질문은 용어 암기보다 “왜 그렇게 되는가”, “이 단계 직후 죽으면 무엇이 남는가”를 묻는다. 읽은 원리를 떠올린 뒤 확인할 수 있도록 답과 근거는 해설 토글에 둔다. 기초 설명 자체는 숨기지 않는다.
6. **점진적 도움 감소와 전이:** 첫 사례는 충분히 풀어 주고 뒤에서는 이미 배운 원리를 다른 문제에 적용하게 한다. 이전 개념의 짧은 재등장은 새 연결을 만들 때만 사용한다. 본문·표·결론의 무의미한 반복은 제거한다.

근거: 미국 교육과학연구소 IES/WWC의 [Organizing Instruction and Study to Improve Student Learning](https://ies.ed.gov/ncee/wwc/PracticeGuide/1) (2007), 권고 2(풀이 예시와 문제), 3(그림과 언어 설명), 4(구체적·추상적 표현 연결), 5(회상 질문), 7(깊은 설명 질문). 선수 지식 점검과 문서 단계화는 이 근거를 기술 교과서에 적용한 편집 판단이며, 학습자별 효과나 수치 개선을 보장하지 않는다. 간격 복습은 선택적으로 다시 읽는 연결로 지원하되 강제 일정으로 만들지 않는다. 학습 유형 분류, 뇌과학 용어를 이용한 과장, 모든 절의 동일 템플릿은 사용하지 않는다.

### 이해 공백 검토

문서 전체를 검토할 때는 각 장의 선수 개념, 실제 가르치는 원리, 추적 가능한 정상 사례, 새 용어, 보장·반례, 다음 장으로 이어지는 이유를 적어 점검한다. 기록은 공개 본문과 별도 원고가 아닌 제외된 작성 자료에 둔다.

- 외부 링크를 열지 않고 사례의 각 단계에서 누가 무엇을 하는지 설명할 수 있는가?
- 설정을 하나 바꾸거나 실패 시점을 바꿨을 때 결과를 앞의 원리에서 도출할 수 있는가?
- 정의 → 실제 사례 → 일반화의 연결이 있는가? 이해를 돕지 않는 분량만 늘지 않았는가?
- 핵심 설명을 부록·용어집·해설로 떠넘기지 않았는가?

정적 검사는 장·앵커·코드·출판 경계를 검증한다. 위 질문에 대한 의미 검토와 실제 독자의 이해 검증은 별개의 절차다. 읽기 흐름을 검토했다고 학습 효과나 독자의 숙달까지 입증했다고 보고하지 않는다.

## 읽기 흐름과 번호

- 장 번호는 1장부터 시작한다. 생소한 용어는 첫 사용 때 한국어 설명과 원어를 함께 제시한다.
- 정상 흐름을 먼저, 실패·예외·보장 조건을 이어 설명한다.
- 한 문단은 한 생각에 집중한다. 정의·동작·비용·예외를 한 문단에 몰아넣지 않는다.
- 단계는 번호 목록, 조건은 짧은 목록, 비교는 표, 공간 관계와 이동은 도식으로 표현한다.
- 반복은 덜되 구조·설계 이유·조건·실패 모델은 보존한다. 가독성 개선은 요약본 축소가 아니다.
- 장 번호 변경 시 목차·본문 참조·부록·그림 캡션·각주 표시 번호·출처 목록을 함께 점검한다.
- 각주의 장 번호는 인용 문장이 있는 장이 아닌 **출처가 정의된 장**을 따른다.
- 공개된 앵커 ID와 링크 대상은 표시 번호와 분리해 보존한다. 링크가 열려도 표시 번호가 틀리면 검증 실패다.
- 사이트 UI·CSS·공통 토글 정책은 별도 요청 없이 바꾸지 않는다.

## 근거와 편집

1. 대상 본문, 승인된 예시 `docs/writing-examples/kafka-pilot.md`, 관련 기존 결정을 읽는다.
2. 공식 문서·프로토콜·구현·고정 릴리스 자료를 실제 조회하고 버전·URL·해당 절을 기록한다.
   이동하는 `current` 문서와 고정 버전 자료를 구분한다. 접근 차단 시 대체 근거와 한계를 밝힌다.
3. 공식 설명·가상 사례·저자의 추론을 구분한다. 수치·기본값·제약·무조건적 보장을 출처와 대조한다.
4. 변경 전후 출처 URL·각주 앵커·코드·이미지·메타데이터를 비교한다.
   통째로 기계 치환하지 말고 변경 대상을 한정한다.
5. 기술 검토와 문체·가독성 검토의 범위를 별도로 보고한다.
   수집·인용·링크 검증만으로 기술 의미까지 검증했다고 하지 않는다.
6. 신규 문서는 저장소의 Wiki 생성 절차를 따른다. 다른 문서의 일괄 수정 권한으로 확대하지 않는다.

## 검증·게시

`AGENTS.md`의 현재 빌드·검증·게시 절차를 따른다.
일반 Jekyll 빌드를 사용하며 출판 경계를 우회하지 않는다.

- 렌더된 목차와 장 순서, 내부 링크 대상, 중복 ID를 검사한다.
- 각주 표시와 출처 목록 번호의 일치, 출처 URL 및 기존 앵커 보존을 검사한다.
- 코드·도식·해설 보존을 확인한다. 다른 기술에 Kafka 전용 검사를 적용하지 않는다.
- 커맨드·작성 지침·테스트·비공개 자료가 공개 빌드에 포함되지 않는지 확인한다.
- 범위에 맞는 검사와 `git diff --check`를 실행한다.
- 시각 변경 시 실제 빌드를 제공하는 미리보기에서 테마·폭·도식·토글을 확인한다.
- 실행·게시 요청은 검증 후 요청 파일만 커밋·푸시한다. 미리보기 전용 요청은 게시하지 않는다.
- 푸시, 해당 커밋의 Pages 성공, 공개 URL의 실제 수정 내용을 각각 확인한다.

완료 보고에는 변경점, 보존한 항목, 검사 범위와 실제 읽을 링크를 포함한다.
