# Kafka 문체 시범

상태: **승인 대기**. 사용자 집필 원문이나 승인된 문체 예시가 아니다. 공개 Kafka 본문에는 아직 적용하지 않았다.

대상: `_wiki/kafka.md` 1장의 `읽은 데이터가 남는 이유: 여러 독자의 독립성` 절. 기준 버전은 Kafka 4.3이며 기술 내용을 추가하지 않고 설명 흐름만 다듬는다.

## 수정 전

### 읽은 데이터가 남는 이유: 여러 독자의 독립성

한 consumer가 읽었다고 레코드가 삭제되지는 않는다. 알림과 정산은 같은 로그를 각자의 위치에서 읽을 수 있다. 정산이 뒤늦게 시작해도 데이터가 남아 있다면 과거 위치부터 읽을 수 있다. 보존 정책은 consumer의 완료 여부와 독립적이므로 무한히 기다려 주지는 않는다. 보존·세그먼트·offset 만료는 읽기와 복구 모델을 배운 뒤 7장에서 다룬다.<sup><a href="../../_wiki/kafka.md#source-1.1">[1.1]</a></sup><sup><a href="../../_wiki/kafka.md#source-1.6">[1.6]</a></sup>

## 수정 후 제안

### 읽은 데이터가 남는 이유: 여러 독자의 독립성

알림 서비스가 주문 이벤트를 읽어도 그 레코드는 삭제되지 않는다. 정산 서비스는 같은 로그를 자신의 읽기 위치에서 읽는다. 뒤늦게 시작하더라도 데이터가 남아 있으면 과거 위치부터 읽을 수 있다.

다만 보존 정책은 consumer의 처리 완료 여부와 관계없이 적용된다. 정산이 끝나지 않았다고 데이터를 계속 남겨 두는 것은 아니다. 보존·세그먼트·offset 만료는 7장에서 다룬다.<sup><a href="../../_wiki/kafka.md#source-1.1">[1.1]</a></sup><sup><a href="../../_wiki/kafka.md#source-1.6">[1.6]</a></sup>

## 편집에서 바꾼 것과 남긴 것

- 추상적인 독립성 대신 기존 사례의 알림·정산 서비스가 무엇을 따로 읽는지 설명했다.
- 읽는 동작과 보존 조건을 두 문단으로 나눴다. 자연스럽게 보이려고 구어체나 감정을 추가하지 않았다.
- 읽어도 삭제되지 않음, 각자의 읽기 위치, 데이터가 남아 있어야 과거부터 읽을 수 있음, 처리 완료 여부와 보존 정책의 분리, 7장 참조와 두 출처를 보존했다.
- 위 출처 링크는 저장소에서 비교할 수 있도록 파일 경로를 사용한다. 본문에 적용할 때는 기존 `#source-1.1`, `#source-1.6` 링크와 헤딩을 그대로 유지한다.

사용자가 문장을 직접 고치거나 채택하면 그 피드백을 기록한다. 승인 전에는 이 예시를 사용자의 말투라고 부르지 않는다.
