# Writing convention

이 저장소의 글을 작성하거나 다듬을 때 적용한다. 작업 진입점은 `AGENTS.md`이며, 글쓰기 세부 기준은 이 문서에서만 관리한다.

## 기준의 상태

사용자는 자연스러운 한국어, 원문과 기술 용어의 보존, 왜·어떻게에 대한 설명을 선호한다. AI 티를 줄이는 규칙과 자신의 문체를 참고할 수 있는 기준을 요청했다.

아래 규칙은 그 요청에 따라 마련한 저장소 편집 기준이다. 사용자의 모든 글에서 추출한 개인 문체 프로필은 아니다. 대화의 말투를 문어체에 그대로 옮기거나, 기존 AI 생성 글을 사용자가 직접 쓴 문체의 증거로 삼지 않는다.

- 사용자 원문: 저자 표현의 근거. 출처와 직접 집필 여부를 확인한다.
- 승인된 편집 예시: 사용자가 결과를 명시적으로 채택한 뒤에만 문체 기준으로 사용한다.
- 승인 대기 예시: 비교를 위한 제안. 기존 본문을 일괄 교체하는 근거로 사용하지 않는다.

## 문장

- 제목을 바로 다음 문장에서 다시 설명하지 않는다. 내용 없는 예고와 반복 결론을 덜어낸다.
- `중요하다`, `효율적이다`, `안전하다`로 설명을 끝내지 않는다. 어떤 동작이 어떤 결과를 만드는지 쓴다. 확인할 근거가 없으면 평가를 빼고 사실만 남긴다.
- 주체가 있으면 주체와 동작을 드러낸다. `독립성을 보장함으로써 유연한 활용을 가능하게 한다`보다 누가 무엇을 따로 읽거나 처리하는지 설명한다.
- `~를 통해`, `~에 대해`, `~측면에서`를 기계적으로 삭제하지 않는다. 문장이 더 직접적이고 정확해질 때만 바꾼다.
- `핵심은`, `결론적으로`, `A가 아니라 B다`를 설명 없이 반복하지 않는다. 실제 구분이 필요한 문장은 유지한다.
- 어미와 격식은 문서 안에서 일관되게 유지한다. 사람처럼 보이려고 종결어미나 문장 길이를 억지로 섞지 않는다.
- 기술 용어는 문서의 기존 표기와 분야의 표준을 따른다. 이해를 돕는 첫 설명은 덧붙일 수 있지만 쉬운 말로 바꾼다는 이유로 정확성을 잃지 않는다.

## 설명과 형식

- 연결되는 설명은 문단으로 잇는다. 절차, 설정값, 비교, 조회가 필요한 내용은 목록이나 표로 남긴다.
- 헤딩, 볼드, 표, 질문을 모든 절에 같은 개수로 배치하지 않는다. 의미 있는 구조와 학습용 확인 질문은 보존한다.
- 위키 본문에 장식용 이모지와 근거 없는 과장 형용사를 넣지 않는다. 경고와 코드 표기는 장식으로 취급하지 않는다.
- 같은 내용을 본문·표·요약에 반복하지 않는다. 참조나 복습에 필요한 반복인지는 먼저 판단한다.
- 담백하게 쓴다는 이유로 배경, 인과관계, 실패 조건, 예외를 지우지 않는다. 짧은 요약과 학습용 설명은 목적이 다르다.
- 처음 소개한 개념은 동작이나 구체적인 상황으로 설명한다. 비유가 개념의 조건을 흐리면 쓰지 않는다.
- 가상 사례는 가상임을 밝힌다. 사용자의 경험, 감정, 판단을 만들어 넣지 않는다.
- 사실, 출처의 주장, 설계상 추론을 구분한다. 윤문을 하면서 불확실한 설명을 단정문으로 바꾸지 않는다.

## 장르별 적용

### 위키·교과서

사실과 동작을 담백하게 설명한다. 개념을 정의하고 필요한 이유, 동작, 조건과 실패 결과를 연결하되 모든 절을 같은 틀에 맞추지는 않는다. 독자가 다시 찾아볼 용어와 링크를 유지한다. 학습자에게 맞춘 설명 순서는 허용하지만 사용자 개인의 공부 계획을 기술적 사실과 섞지 않는다.

### 개인 글·회고

사용자가 쓴 문장의 감정, 망설임, 질문, 생각의 변화를 보존한다. 객관적인 레퍼런스 문체를 강제하거나 매번 교훈과 결론을 붙이지 않는다. 실제 경험이나 신앙적 해석을 대신 만들어 쓰지 않는다.

### 리뷰

감상과 평가의 정본은 사용자 원문이다. 별도 윤문 요청이 없으면 표현과 문장부호를 보존한다. 소개문, 평점, 감상, 완료일을 추측해서 채우지 않는다.

## 편집 절차

1. 문서의 목적과 장르, 원문, 기존 용어와 출처를 읽는다. 사용자가 승인한 해당 장르의 예시가 있으면 함께 읽는다.
2. 내용 검토와 문체 검토를 구분한다. 기술적 결함은 출처를 확인한 뒤 수정하고, 문체 수정과 별도로 보고한다.
3. 의미 없는 예고·중복·추상 표현 등 실제 문제가 있는 구간만 고친다. 이미 자연스러운 문장은 그대로 둔다.
4. 원문과 대조해 사실, 수치, 조건, 인과관계, 단언의 강도, 기술 용어가 유지됐는지 확인한다.
5. 코드, 그림, 표의 값, 링크, 앵커, 목차 생성 구문, 프론트매터를 보존한다. 구조를 바꿨다면 참조와 렌더링을 검증한다.
6. 개인 문체의 첫 시범 편집은 별도 제안으로 보여준다. 사용자 승인 전에는 그 문체를 전체 글에 적용하지 않는다. 이미 승인된 범위의 편집에 불필요한 재승인을 요구하지 않는다.

단어 검색이나 빌드 성공만으로 문체 검토가 끝났다고 판단하지 않는다. 수정 문장을 실제로 읽고 앞뒤 맥락과 비교한다.

## 문체 예시 관리

사용자가 직접 쓴 기준 글은 아직 이 문서에 등록하지 않았다. 등록할 때는 공개 가능한 문단을 사용자가 선택하거나 확인하고, 원문 위치와 장르를 함께 기록한다. 비공개 대화나 업무 자료를 공개 저장소에 복사하지 않는다.

[Kafka 편집 예시](writing-examples/kafka-pilot.md)는 2026-10-06 사용자가 승인했다. 구체적인 서비스 동작을 직접 설명하고 읽는 동작과 보존 조건을 분리하는 문장을 위키 편집 기준으로 삼는다. 같은 요청에서 Kafka 문서 전체 적용도 승인했다. 사용자 직접 집필 원문이나 모든 장르를 아우르는 개인 문체 프로필은 아니며, 다른 문서의 일괄 재작성·게시까지 승인한 것은 아니다.

이 지침과 편집 예시는 Jekyll의 `docs` 제외 규칙에 따라 사이트에는 출판하지 않는다. GitHub 저장소에서는 읽을 수 있으므로 비밀이나 개인 원문을 넣지 않는다.
